# inform9 Planning Review

## Context
Todd asked for a review of everything in `planning/` before build starts. inform9.com is owned; no page designs exist yet. Files reviewed in full or by structure: pr-faq.md, use-cases.md (24 UCs), functional-requirements.md/.csv (275 reqs), test-cases.md (113 TCs), ArchitectureGuidelines.md, engineering-prompt-overview.md.

Product docs (PR/FAQ → use cases → requirements → test cases) are consistent with each other and thorough. The main problem is that the two engineering docs describe a different, smaller product.

## Findings

### 1. Architecture docs describe a smaller app than the use cases (highest priority)
Model (per Todd): one inform9 platform, run by inform9. Any business user can sign up for an account, and each account can hold several businesses (orgs). Payees can also have accounts.

ArchitectureGuidelines.md and engineering-prompt-overview.md describe one intake form feeding one admin dashboard, with one admin login. Missing from the architecture:
- Three sign-in types: Business Owner, Payee, inform9 Administrator. "/dashboard" in the architecture is the inform9 admin; in the use cases the main signed-in app belongs to each Business Owner. Needs a route map (public / owner app / payee app / internal admin).
- Account-level data separation: each Business Owner sees only their own businesses, payees, and W-9s, so every D1 query filters by account (and business).
- Email provider, bounce webhooks, one-time codes, verification and reset links.
- Scheduled work for reminders (Cron Triggers or Queues), with the one-reminder-per-day-per-payee rule.
- Payment processor (Stripe or similar) and its webhooks.
- Rate limits and abuse controls (send caps, opt-out list, code attempt lockouts).
- Payee saved profile, W-9 versioning, share records, download logs, audit logs.

### 2. Platform limits
- Workers Free plan allows 10 ms CPU per request. pdf-lib fill/flatten and password hashing will exceed it. The $5/month Workers Paid plan removes this; the doc should say Paid is the baseline.
- Workers caps PBKDF2 at 100,000 iterations. Pick and document the password hashing approach.
- Decision (Todd, 2026-10-08): TypeScript on Cloudflare for the MVP. Astro front end, TypeScript Workers backend, D1, R2, pdf-lib, signature_pad, fflate as the guidelines already name. Remove "RUST may be best" from the guidelines. Note Rust on Fly.io (Axum, SQLite + Litestream, PDFs in R2) as a possible later move if Workers limits start to hurt.
- Use the $5/month Workers Paid plan as the baseline, since the Free plan's 10 ms CPU limit is too low for PDF work and password hashing.
- Password hashing: PBKDF2-SHA256 at the Workers maximum of 100,000 iterations with a per-user salt, stored with the iteration count so it can be raised later.
- Cloudflare now steers new projects to Workers with static assets over Pages. Worth confirming before scaffolding.
- Guidelines say stream the ZIP; the engineering prompt says Promise.all and "packages them in-memory." These conflict with the 128 MB memory limit. Stream it.

### 3. Security gaps
- Signed W-9 PDFs in R2 contain the full TIN in plain form. Encrypting only the D1 column leaves the PDFs exposed. Encrypt PDFs at the app level too, or accept and document R2 provider encryption.
- No key versioning or rotation plan for the AES-GCM key.
- MFA is still open (UC Create Account). Given TIN storage, decide before beta.
- Store a hash of each generated PDF in the audit record so tampering is detectable.
- Track the W-9 form revision (currently Rev. March 2024) used for each PDF; templates change.
