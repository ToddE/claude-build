# inform9 Build Plan

## 1. Tools and structure (decided)

| Area | Choice |
| --- | --- |
| Language | TypeScript, strict mode, on Node 22 for tooling and Cloudflare Workers for runtime |
| Package manager | pnpm workspaces |
| Site | Astro in hybrid mode with the Cloudflare adapter. Public pages are static. App, payee, admin, link, and opt-out routes render on the server |
| API | One Cloudflare Worker using Hono for routing and Zod for validation. It also holds the cron handler. It serves `inform9.com/api/*` |
| Site to API | A service binding, so the site's middleware asks the API for the session |
| Data | D1 (SQL migrations), R2 for PDFs and backups |
| PDF | `pdf-lib`. Signature from `signature_pad` in the browser |
| ZIP | `fflate`, streaming |
| Crypto | Web Crypto only: AES-256-GCM and PBKDF2-SHA256 |
| Tests | Vitest with the Workers pool for the API, Playwright for end-to-end, axe for accessibility |
| Lint | ESLint, Prettier, and the two site rule checks from the [site rules](site-content-and-style-rules-2026-10-08-1543.md) |
| Dependency versions | Latest stable at scaffold time, pinned in the lockfile |

```
inform9/
  apps/
    site/                     Astro. src/pages, src/components, src/layouts, src/content, src/styles/global.css, public/
    api/                      Hono Worker. src/routes, src/services, src/jobs, src/db
  packages/
    shared/                   Zod schemas, enums, status rules, settings definitions, formatters
    email/                    render.mjs, layout.html, email.css, messages.json, build and test scripts (from planning/email)
  migrations/                 0001_schema.sql, 0002_seed_settings_and_plans.sql
  scripts/                    check-site-rules.mjs, seed-admin.mjs, dev helpers
  tests/                      api, e2e, fixtures (sample W-9 template, sample signature, sample emails)
  planning/                   these documents
  .env.example  .env.local  .dev.vars
```

At the start (M0), copy `planning/brand/` into `apps/site/public/brand/` and `planning/email/` into `packages/email/`. The code copies are the working versions from then on. `planning/schema-*.sql` becomes `migrations/0001_schema.sql`, and the settings and plans rows in the [data model](data-model-2026-10-08-1352.md) become `0002`.

## 2. Rules for the builder

1. Follow the [decisions log](decisions-log-2026-10-08-1545.md). Do not ask about anything it answers.
2. When something is unanswered, choose the safer and simpler option, add a row to section 7 of the decisions log, and continue.
3. Build one milestone at a time. A milestone is done only when its checks in section 4 pass.
4. Use cases, requirements, and test cases are the specification. When code and a requirement disagree, the requirement wins. If a requirement is wrong, fix `functional-requirements.md` and say so.
5. Copy and style follow the [site rules](site-content-and-style-rules-2026-10-08-1543.md) and the [copy instructions](copy-drafting-instructions-2026-10-08-1544.md).
6. Never log, return, or display a taxpayer ID, password, link token, session token, or provider key.
7. Commit at the end of each task, with a message that names the use case and requirement IDs.

### Stop only for

| Reason | What to do |
| --- | --- |
| A credential or DNS record from the checklist is needed to continue | Name the variable and the step, then continue with a mock if one exists |
| Legal or security text that the decisions log assigns to a person | Write the draft with its `[CONFIRM]` or `[LEGAL REVIEW]` marker and continue |
| A test fails after three fix attempts | Report the failing test and what was tried |
| A change would weaken a security rule in [ArchitectureGuidelines.md](ArchitectureGuidelines.md) | Stop and ask |
| The milestone review gate in section 3 | Report results and wait only if the milestone says "gate" |

## 3. Milestones

Each lists what to build, the use cases it covers, and the gate.

### M0. Repository and tooling

- Scaffold the workspace in section 1. Strict TypeScript, lint, format, and test commands. Wrangler configs for the site and the API with D1, R2, and the service binding. Local D1 and R2 through `wrangler dev`.
- Load `.env.local` for the site and `.dev.vars` for the API. Validate every variable at start.
- Run the migrations. Load `email/dist/templates.seed.sql`.
- Settings service: read a value from the database, then the environment (`SETTING_<key>`), then the default, check it against its range, and cache it for 30 seconds.
- Audit log helper, ID and time helpers, error type with the codes in the [API spec](api-spec-2026-10-08-1522.md).
- Email provider interface with the SMTP2GO adapter and a console adapter. The template renderer from `packages/email`.
- Crypto service: AES-256-GCM with key ids, PBKDF2 hashing, hashing of tokens, constant-time compare. Unit tests including a key rotation round trip.
- `scripts/check-site-rules.mjs` and a stub `global.css` with the tokens.

Done when: lint, type check, and unit tests pass, and `pnpm dev` serves a blank branded page with the font files loading from the site.

### M1. PDF spike (gate)

- Fetch the official IRS W-9 into `tests/fixtures/`, record its revision, and list its form fields.
- In the API, fill every field, stamp a requester name and address, stamp the signature PNG, add the receipt block, flatten, encrypt, write to R2, read back, decrypt, and compare the hash.
- Render the output PDF to images and check text positions in at least two viewers.
- Record CPU time and memory for one PDF and for three PDFs from one request.

Done when: the round trip passes in a test, the output looks correct, and the report states timing against Workers limits. Gate: report the results before M2. If the form fields cannot be filled, switch to coordinate placement and say so.

### M2. Accounts, sessions, and the site shell

- API: sign-up, verify, resend, sign-in with lock, sign-out, password forgot and reset, password confirm, `/me`, preferences, sessions, idle and absolute timeout, rate limits, Turnstile check, the breached-password check.
- Site: base layout, header, footer, notices (including the cookie notice), the content collections and schemas, the screen and form components, the full `global.css` for the components in the inventory, and middleware that guards `/app`, `/payee`, `/admin`.
- Content: the catalogs in the [copy instructions](copy-drafting-instructions-2026-10-08-1544.md), section 7, and the screens signup, signup-sent, verify, signin, reset-request, reset-set, app-home.
- Emails: verify_email and reset_password through the console adapter.

Covers: Create Account and Sign In, Reset Password, Sign Out. Tests: TC-CreateAccount, TC-ResetPassword, TC-SignOut.

Done when: those test cases pass end to end in the browser and the API, the site rule checks pass, and axe finds no serious issues on these pages in light and dark.

### M3. MVP, for inform9's own use

- Businesses and payees: Add Business, Edit Business, Add Payee Contact, Edit or Archive Payee, with the free plan limits and the upgrade message (no checkout yet).
- Requests: Request W-9, Follow Up on Incomplete Request, Cancel Request.
- Payee link flow: Complete and Sign W-9 (form, review with the signature pad, submit), Payee Declines Request, link problem screen, foreign payee path. One PDF per business, encrypted, stored, version rows, request completed.
- Owner views: payee list with the five statuses and notes, payee detail, download with the password confirmation, View and Download W-9s.
- Emails: request, payee_received, owner_completed, owner_declined, owner_delivery_failed. Bounce webhook for SMTP2GO.
- Content for all of these screens.

Covers: Add Business, Edit Business, Add Payee Contact, Edit or Archive Payee, Request W-9, Complete and Sign W-9, Payee Declines Request, View and Download W-9s, Follow Up on Incomplete Request, Cancel Request. Tests: the matching TC groups.

Done when: those tests pass, a full run works in the browser (sign up, add a business and a payee, send a request, complete it on a phone-size window, download the PDF), and the PDF is correct. Gate: Todd uses it for real W-9s for inform9 itself.

### M4. Beta

- Payee accounts: Create Payee Account, Confirm and Reuse Saved Payee Information, Update a W-9, saved profile, payee home.
- Reminders: the cron job, Send W-9 Reminders (including Stop reminders and combined emails), Set Reminder Schedule, Reminders ended note.
- Export Payee Data: both CSV formats, general CSV, streaming ZIP.
- Plans and money: Upgrade After Free Limit with Stripe Checkout and webhook, billing status. Cancel Account and Data Handling. Manage Communication Preferences.
- Administrator: separate sign-in with a second factor, Configure Platform Settings (all groups, provider keys, test email, payment test, email message editing), audit log screen.
- Backups: scheduled D1 export to R2, with a restore test.
- Content for these screens. Emails for the beta set.

Covers the use cases named above. Tests: the matching TC groups.

Done when: those tests pass, reminders send on schedule against a test clock, Stripe test checkout works end to end, the settings screens change real behavior, and a restore test succeeds. Gate: security review of crypto, sessions, and the PDF flow before real users.

### M5. Public launch

- Payee-sent W-9s: Payee Sends W-9 to Business, Limit Unsolicited Sends, Business Recipient Retrieves Payee-Sent W-9, Save Payee-Sent W-9 to Account, Opt Out of Payee-Sent W-9s, View Sent W-9s.
- Review Abuse Flags with the pause and block rules.
- Unsubscribe, the public pages, Umami on public pages, the sitemap, and the robots rules (no indexing of app and link pages).
- Hardening: Content Security Policy, security headers, rate limits tuned, error pages, log scrubbing check, dependency audit.
- Performance and accessibility pass across every screen. Email tests in Gmail, Outlook, and Apple Mail.
- Runbook: deploy, rollback, key rotation, restore, incident steps.

Done when: all 151 test cases pass, the site rule checks and axe pass on every built page, and the launch gates in section 6 of the decisions log are closed.

## 5. Test approach

- Each test case in [test-cases.md](test-cases.md) becomes one automated test with the same id in its name. The test follows the steps and asserts the expected result. A coverage script lists test case ids with no test.
- API tests use a clean local D1 and R2 per test file, a fixed clock, and the console email adapter that records messages for assertions.
- End-to-end tests cover the flows that cross screens: sign-up to first request, payee completion, reuse of saved information, reminders, export, upgrade, payee-sent retrieval.
- Fixtures: a sample W-9 template, a sample signature image, sample payees, and a Stripe webhook payload set.
- Security tests: a taxpayer ID never appears in logs or API responses, a request owner cannot read another account's records, expired and reused tokens fail, rate limits and locks trigger, and cookies match the rules (one cookie, correct flags, none on public and link pages).

## 6. Traceability

Requirement ids appear in code comments at the function that satisfies them. A script reads `functional-requirements.md` and lists requirement ids with no reference. The release is blocked while any Must requirement has none.
