# inform9 Model Routing

## 1. Rule of thumb

Use the least expensive model that can do the task correctly. Use a stronger model where a mistake would expose taxpayer data, lose data, or take money wrongly, and where a subtle bug would not show up in a test.

| Model | Use it for | Share of tasks |
| --- | --- | --- |
| **Opus 5.5** | Security-critical code (encryption, sign-in and sessions, account isolation, PDFs with taxpayer IDs, payments, data deletion), design questions that cut across the system, hard debugging, and every review gate | About 24% |
| **Sonnet 5.5** | Most of the build: endpoints, screens, components, jobs, tests, copy, and updating the planning documents | About 66% |
| **Haiku 5.5** | Mechanical work with a clear right answer: config, fixtures, seed data, renames, lint fixes, running checks and summarizing the result | About 10% |

Fable 5.1 is not assigned here because I have no basis yet for where it fits. The table can add it after a trial on one task.

Choose once and choose right. A task that fails on a cheaper model and is repeated on a stronger one costs more energy than starting on the right model. So there is no "try cheap first" step.

### How to pick the model for a task

Ask in this order and stop at the first yes.

1. Would a mistake be silent and harmful, meaning it could expose taxpayer data, take money wrongly, or delete data, and would a passing test still miss it? **Opus.**
2. Is the task a design question that touches several parts of the system, or a hard bug that has already resisted a fix? **Opus.**
3. Could a script do it, and does one command fully verify the result, with no judgment involved? **Haiku.**
4. Everything else, including Astro screens and components, API endpoints, jobs, tests, copy, and documents. **Sonnet.**

When two answers fit, take the higher model. A task is never started on a lower model on the chance that it works.

The main session runs on Sonnet and coordinates. It hands each task to the agent in section 5 with only the files that task needs.

## 2. When a task fails

Do not repeat the whole task on another model. Repeating is the costly step.

| Situation | Action |
| --- | --- |
| A check fails | Read only the failing output, fix the cause on the same model, and run only the affected check |
| It fails a second time | Stop. Write a three-line diagnosis (the failing check, what was tried, the suspected cause) and hand that, with the failing files, to Opus. Do not restart from the beginning |
| A Haiku result needs judgment, or passes only by changing a test | The row was misclassified. Reclassify it to Sonnet in the table so the next task of that kind starts correctly |
| Any change touches the protected paths in section 3 | An Opus review of the diff, not of the whole file, before the task is done |
| A requirement conflicts with another requirement or with the architecture | Opus decides, records it in section 7 of the [decisions log](decisions-log-2026-10-08-1545.md), and updates `functional-requirements.md` |

## 3. Protected paths (Opus writes them; no second pass unless the diff changes)

- `packages/shared/crypto*` and anything calling `crypto.subtle`
- `apps/api/src/auth/`, session handling, password hashing, MFA, and `apps/site/src/middleware*`
- The data access layer that filters by account
- PDF generation, storage, decryption, and every route that returns or exports a W-9 or a taxpayer ID
- Stripe checkout, the Stripe webhook, and plan changes
- Account cancellation, retention, and deletion jobs
- Share-link one-time codes, bearer tokens, and download caps
- Content Security Policy, security headers, and log scrubbing
- Provider key storage in the `secrets` table

## 5. Agents

The agent files are in `.claude/agents/`. Each one sets its model.

| Agent | Model | Handles |
| --- | --- | --- |
| `builder` | Sonnet | Feature code, Astro screens and components, jobs, and tests |
| `copywriter` | Sonnet | Site and screen copy, following the copy instructions |
| `mechanic` | Haiku | Config, fixtures, seeds, renames, lint, and running and summarizing checks |
| `security` | Opus | Everything in section 3, and the protected-path reviews |
| `gate-reviewer` | Opus | Milestone gates, requirement conflicts, and final reviews |

The main session reads the task table, picks the agent, and passes it the task id, the files to read, and the checks that must pass. The agent reports what changed and the check results.

### Effort level

Effort controls how much the model reasons before it answers. It uses the same rule as the model choice: set it once, to what the task needs. A higher level on a simple task burns tokens for nothing. A lower level on a hard task causes errors that cost a redo.

| Level | Use it when | Default for |
| --- | --- | --- |
| low | The task is scripted and one command verifies it | `mechanic` |
| medium | The task is built from a clear spec and checked by tests or scripts | `builder`, `copywriter` |
| high | A mistake could be silent and harmful, or the task is a design question | `security`, `gate-reviewer` |
| xhigh | The result decides whether real taxpayer data goes live | The overrides below |

Overrides for single tasks:

| Task | Effort | Why |
| --- | --- | --- |
| 0.8 Crypto service | xhigh | Protects every secret |
| 1.2 and 1.3 PDF fill and encrypted storage | xhigh | Taxpayer data in a document |
| 3.2 Account-scoped data access | xhigh | A leak exposes another customer |
| 4.6 Stripe checkout and webhook | high | Money, with a signature check |
| M4 and M5 security review gates | xhigh | Last review before real users |
| 2.9, 3.11 Tests written from explicit test cases | low | The steps and expected results are already written |
| 3.6, 5.6 Simple screens from content | low | The pattern is fixed and the site rule checks confirm it |

The agent files in `.claude/agents/` carry the defaults in an `effort` line. A task that needs an override says so in its task packet. If Claude Code does not read the `effort` line in an agent file, set the level when the agent is launched, and check with `/agents` that the files are recognized.

If a lower setting causes a failed check, raise the effort for that kind of task in this table. Do not rerun the same task at a higher level.

## 6. Token and energy practices

These apply to every agent. They matter as much as the model choice.

1. **Read only what the task needs.** The use cases, requirements, and test cases are each about 25,000 to 30,000 tokens. Search by requirement id or section heading and read that part. Never open a whole planning file for one rule.
2. **Give each agent a task packet,** not the whole project: the task id, the file and line ranges to read, and the checks to run. A cold agent that explores uses far more tokens than one that is pointed.
3. **Let scripts do the checking.** Lint, types, tests, the site rules, and the email checks run as commands. Show the model only the summary line and the failing items, not the full log.
4. **Run the narrowest check first.** Run the tests for the files changed. Run the full suite and the end-to-end tests at milestone gates, not after every edit.
5. **Edit, do not rewrite.** Change the lines that need changing. Do not regenerate a file to alter a few lines.
6. **Do not review what checks already prove.** Opus reviews protected-path diffs and gates. It does not re-read routine code that passed its tests.
7. **Batch small tasks of one kind** into one agent run so the context is loaded once.
8. **Avoid images and screenshots** unless a visual check is the task. They cost many tokens. Prefer the accessibility scan and the site-rule script.
9. **Stop searching once found.** One targeted search beats a broad sweep.
10. **Keep `CLAUDE.md` short.** It loads in every session.
11. **Generate with code when the output is repetitive.** The 22 email messages render from data; screens render from content files. Do not ask a model to write what a template produces.
